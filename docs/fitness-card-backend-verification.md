# Fitness Card backend verification

The canonical migration is `infra/supabase/migrations/20260912040000_fitness_card.sql`. The SQL runner described below verifies a disposable local PostgreSQL instance. The migration was subsequently applied remotely at the user's request; live schema/ACL, function-body, ledger and anonymous HTTP checks are recorded in [fitness-card-verification.md](fitness-card-verification.md#activation-and-remaining-external-verification). Authenticated Storage transfers, Realtime delivery and physical-device behavior remain separate checks.

Run `node mobile/src/original/run-fitness-card-postgres.mjs --native` with PostgreSQL 17 available at `C:/Program Files/PostgreSQL/17/bin`, or set `FITNESS_CARD_POSTGRES_BIN`. The default without `--native` uses the existing Supabase PostgreSQL Docker image. The runner creates and cleans up only its disposable database cluster, loads every canonical migration, and exercises authenticated roles against the real PostgreSQL engine.

The initial `--red --native` run failed with `Fitness card contract missing` before implementation. Green contracts cover explicit card creation, CAS rejection, minimal evidence shape and bounds, unknown and null JSON fields, invalid/future civil dates, exact 84-day ranges, directed sharing, pending authorization, multiple viewers, owner acceptance, reject/cancel/leave/revoke, stale request IDs, inactive accounts, case-ambiguous handles, Storage RLS, exact three slots, photo revision changes, private function/table grants, and signals delivered to a removed viewer. Separate simultaneous SQL connections exercise competing CAS edits and concurrent photo mutation/revocation; later viewer reads and Storage SELECT are denied.

Storage policies are tested with RLS enabled and authenticated SELECT/INSERT/UPDATE/DELETE grants in the platform fixture. The actual bucket enforces WebP and 2 MiB through Supabase Storage. The fixture proves policy decisions, paths and database mutations, not HTTP MIME validation or image-byte processing. Realtime publication registration is conditional on an existing `supabase_realtime` publication; the table contains only per-user revision/timestamp signals, with own-row SELECT and no client writes.

All card/access/photo mutations share one small feature-specific advisory transaction lock to establish a consistent order. Save and evidence publication require the exact current card revision; create uses revision zero. Photo storage changes increment card revision automatically, so clients must refetch before a later CAS edit. Profile identity/account-status changes notify all related participants, including viewers without their own card. Received content must stay in memory and obey the client authorization lease; server checks cannot erase images already downloaded.
